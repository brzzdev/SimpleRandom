# The app never claims more about sync than it can know

One discipline, applied in both directions.

**It never says "Up to date."** There is no initial-sync-complete signal in the public API, and `isFetchingChanges` is `false` *before* the first fetch begins, so an idle engine is indistinguishable from a finished one. "Up to date" would be a false claim on first launch — precisely when a user most wants reassurance. The Settings `Sync` row shows account availability plus a transient "Syncing…" while `isSynchronizing`, and is worded so its absence reads as "nothing in flight", not "everything landed".

**It never says "Couldn't sync" either.** `SyncEngine` swallows essentially every CloudKit error — network failure, service unavailable, quota exceeded, rate limited, not authenticated — into a `continue`, with no rethrow, no delegate callback and no observable error property. There is no error to bind a UI to without inventing one, and inventing it means probing `accountStatus` and tracking a last-successful-fetch the library does not provide. A false "Couldn't sync" on a healthy device is worse than silence, and the failures being guarded against are transient blips the engine already retries. So: no banner, no failure row, ever.

## Consequences

- **`View Logs` ships in release builds** and is the whole diagnostic surface. A debug-only viewer would be absent from exactly the builds — TestFlight, App Store — where sync problems actually show up. App-side database writes are wrapped in `withErrorReporting` so *local* failures, the ones that really lose data, are logged too.
- **`hasCompletedFirstFetch` is the one exception**, and it earns it. A device-local, one-way `@Shared(.appStorage)` flag is set once the first fetch returns; until then, **and only when an iCloud account is available**, the Lists and Combine tabs say they are checking iCloud rather than that they are empty. This is the one place sync's invisibility does real damage, because the user acts on the lie — they recreate lists that already exist and the duplicates sync back. It degrades correctly in both directions: no account skips it, a failed fetch leaves it `false` and retries next launch.
- **Pull to refresh** on both index tabs is the only manual control. It is a *fetch*, not a sync — local changes are already queued and sending on their own — and it promises nothing about having finished. A `Sync Now` row in Settings was rejected: a manual sync button implies sync is something you manage, which this ADR says it is not.
- **No per-record sync state.** The metadata database is not attached, so there is no per-row "not yet synced" badge. That would explain sync at a granularity everything above deliberately avoids. Unlike the schema decisions this one is fully reversible — one line in `prepareDatabase` — and sharing would need it anyway.
- **Sorting breaks ties on `id`.** `createdAt` alone is not a total order, so two devices creating rows offline in the same second render the same data differently, with no reorder gesture to blame it on. Breaking on the primary key is arbitrary but *identical everywhere*, which is strictly better. It does not fix clock skew, and nothing short of a logical clock would.
